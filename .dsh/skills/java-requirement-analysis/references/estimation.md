# 估时（estimation）

单位：**人天（8 小时）**，最小粒度 **0.25**。给的是工作量区间，不是交付日期。

## 公式

```text
base   = Σ estimate.parts[].days
factor = Π estimate.factors[].multiplier      （没有因子就是 1）
p50    = ceil(base × factor × 4) / 4
p90    = ceil(p50 × buffer × 4) / 4           （buffer 默认 1.5，范围 1.2–2.0）
```

`p50` / `p90` 一律由 `req.mjs estimate` 计算并写回；手填的值会被 `validate` 判为过期。

## 基线：按「改动点」取，不按子需求拍脑袋

| 改动点 | 基线人天 | 说明 |
| --- | --- | --- |
| 修改既有接口（不改契约） | 0.25 | 加校验、改逻辑 |
| 修改既有接口（改契约） | 0.5 | 同步改调用方 |
| 新增查询接口 | 0.5 | Controller + Service + Mapper + DTO |
| 新增写接口 | 1.0 | 含校验、事务、幂等、错误码 |
| Entity / DTO / VO 加字段 | 0.25 | 单层；跨 3 层以上 0.5 |
| 表加字段 / 索引 | 0.25 | 不含迁移 |
| 新表 | 0.5 | 含 Entity/Mapper |
| 数据迁移 / 刷数 | 1.0 | 含回滚与校验；大表 +0.5 |
| 工作流节点处理 | 1.0 | 改 extHandler |
| 新增流程分支 / 节点 | 1.5 | 含流程定义与回归 |
| 状态机加状态 | 0.5 | 含枚举、前端映射 |
| 页面：列表 / 表单 | 1.0–2.0 | 按字段数与交互定 |
| 页面：复杂交互 | 2.0–4.0 | 树、拖拽、富文本、批量 |
| 菜单 / 按钮权限 | 0.25 | 数据权限规则 0.5–1.0 |
| 定时任务 | 0.5 | 分批/断点/补偿 +0.5 |
| MQ 生产或消费 | 0.5 | 加补偿 +0.5 |
| 外部集成（单接口） | 1.0–2.0 | 含联调与异常分支 |
| 外部集成（回调/对账） | 2.0–3.0 | |
| 配置 / 字典 | 0.25 | 含多环境 |
| 报表 / 导出 | 1.0–2.0 | 异步导出取上限 |
| 非功能改造 | 0.5–2.0 | 按验证成本 |

**测试与联调不要漏**：一般按开发工作量 ×0.3（简单）到 ×0.5（跨仓库/外部依赖）单列为 `parts` 的一项，别塞进开发里。

## 因子：只加有证据的

| 因子 | 倍数 | 证据要求 |
| --- | --- | --- |
| 动核心表 / 核心流程 | ×1.3 | `core.json` 里有标记，或表被 3 处以上读写 |
| 无同类样例（新模块） | ×1.5 | `find` / `context` 找不到可参照的同类类 |
| 多环境验证（dev/test/uat/prod） | ×1.2 | 需求明确要求逐环境验证 |
| 历史兼容 / 双写 / 灰度 | ×1.3 | 有存量数据或老客户端 |
| 首次接第三方 | ×1.3 | 无现成适配层 |

因子是乘法的，叠 3 个以上要复核：`1.3×1.5×1.3 ≈ 2.5`，通常意味着应该拆需求，而不是继续乘。

## parts 怎么拆

一个子需求至少两项：

1. **开发**：后端/前端分开列；
2. **自测**：写单测、造数据、回归旧功能；
3. **联调**：跨仓库、第三方、前后端联调——单列；
4. **文档/评审**：接口文档、DDL 评审——必要时单列。

> 只有一行 `"开发": 2` 的估时视为未估。

## 需求级汇总

```text
需求 P50 = Σ 子需求 P50 + 评审/统筹（默认 +10%）
需求 P90 = Σ 子需求 P90 + 评审/统筹（默认 +10%）
```

- 评审/统筹包含：需求评审、技术方案、排期沟通、上线支持；
- 并行开发时，**人天不等于日历天**：日历天 ≈ 人天 ÷ 并行人数 × 1.2（沟通损耗）；
- 对外只报区间（P50–P90），不报单点。

## 示例

```json
"estimate": {
  "parts": [
    { "name": "后端接口与事务", "days": 1.0 },
    { "name": "联调签章服务", "days": 0.5 },
    { "name": "自测与文档", "days": 0.25 }
  ],
  "factors": [{ "name": "动核心流程", "multiplier": 1.3 }],
  "buffer": 1.5
}
```

```text
base   = 1.75
factor = 1.3
p50    = ceil(1.75×1.3×4)/4 = ceil(9.1)/4 = 2.5
p90    = ceil(2.5×1.5×4)/4  = ceil(15)/4  = 3.75
```

结论：2.5 人天（P50），3.75 人天（P90）。

## 反模式

| 反模式 | 为什么不成立 |
| --- | --- |
| 只写一个总数 | 无法复核，也无法在需求变更时增量调整 |
| “按经验大概 3 天” | 经验要落到改动点清单上，否则不可审计 |
| 把 buffer 当项目风险 | buffer 只覆盖估算误差；排期风险（人力、依赖）另算 |
| 用功能点/故事点代替人天 | 团队没做基线校准前，故事点换不成排期 |
| 先定交付日期再倒推人天 | 顺序反了：先给区间，再由管理者决定砍范围还是加人 |
