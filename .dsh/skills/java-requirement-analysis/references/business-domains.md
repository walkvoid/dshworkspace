# 业务域（business domains）

技术大类（`category`）回答“改成什么”，业务域（`domain`）回答“**这是哪块业务的事**”。
一条子需求**两个维度都要填**：先归业务域，再标技术大类。

供应链金融平台的 12 个固定业务域：

| id | 业务域 | 包含 | 不包含 | 典型对象 |
| --- | --- | --- | --- | --- |
| `cust` | 客户与建档 | 企业建档、建档变更、经办人/账户变更、实名与面签、协议签署 | 产品开通、额度 | `cust_company_info`、`cust_user`、`cust_agreement` |
| `product` | 产品与开通 | 产品中心、产品开通/激活、单点登录、登录角色、报价 | 建档本身、额度 | 产品配置、`product_*` |
| `limit` | 额度 | 开单额度、融资额度、额度同步/占用/释放、额度审核 | 报价、资产 | `limit_info`、`apply_limit_info` |
| `asset` | 资产与凭证开立 | 资产导入/维护/审核、开立、确权、签收、合同签署 | 转让/融资、作废、兑付 | `ast_asset*`、`ts_asset` |
| `trade` | 凭证流转与融资 | 转让、融资申请、放款、直保、资金方准入 | 开立、作废、兑付 | 交易、融资单 |
| `abolish` | 凭证作废 | 作废预申请、作废审核、作废结果通知 | 开立失败删除、兑付 | `ts_asset_abolish_apply` |
| `repay` | 兑付与结清 | 到期兑付、线下兑付确认、结清、逾期 | 融资还款（归 `trade`） | 兑付明细、还款计划 |
| `query` | 查询与统计 | 查询中心、持有/交易/放款台账、驾驶舱、报表导出 | 监管报送 | 查询服务、统计 SQL |
| `report` | 监管报送 | 互金协会报送、发票报送、监管口径 | 内部报表 | 报送任务/接口 |
| `notify` | 通知与预警 | 站内信、短信、邮件、企微告警、重试 | 业务状态机本身 | 消息模板、告警服务 |
| `channel` | 渠道与集成 | 单点登录、外部接口适配、银行/资方对接、文件交换 | 内部业务规则 | 适配层、网关、签名 |
| `platform` | 平台与配置 | 菜单/权限、字典、参数、调度、部署 | 具体业务功能 | 配置表、权限模型 |

## 归类规则

1. **看“业务对象”而不是“技术落点”**：改的是 `cust_company_info` 就是 `cust`，哪怕动的是工作流；
2. **一个子需求一个主域**：跨域放 `secondaryDomains`（最多 2 个），但不要用“平台”“渠道”兜底——
   兜底说明你还没想清楚业务归属；
3. **“渠道与集成”只给纯通道类改动**：单点登录换码、银行接口适配；带业务规则的推送（如建档推送）归业务域；
4. **同一业务域内再按技术大类分**：先按域聚合，域内再看是 api / schema / flow / job；
5. **域的名字用需求方的话**：客户说“建档”，就用 `cust` 建档案；不要造“客户主数据治理”这种词。

## 为什么要分域

- **排期按域走**：一个域通常对应一个业务小组/一位产品，域内子需求能并行、域间才需要联调；
- **估时更稳**：同域的需求复用同一批类、表、测试数据，边际成本递减；
- **漏项早暴露**：域分布表里某个域 0 条，往往意味着漏了一整块（比如只有开立没有作废）；
- **报告更好读**：业务方看域，技术看大类。

## 与 `category` 的配合

```json
{ "domain": "cust", "category": "integration", "secondary": ["flow"] }
```

读法：**客户建档域**的一次**外部集成**改造，附带**流程**变化。
报告里先给域分布（业务视角），再给大类分布（技术视角），最后逐条列子需求。
